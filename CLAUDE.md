# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build
cargo build              # debug
cargo build --release    # release (used by run_tests.sh)

# Run
cargo run                        # REPL
cargo run -- path/to/script.lisp # run a .lisp file

# Test — golden-file comparison, no cargo test harness
./run_tests.sh            # builds release, diffs output of tests.lisp / new-features.lisp /
                           # hello.lisp / swarm.lisp / symreg-test.lisp / synth-test.lisp / prover-test.lisp / robot-test.lisp / pkg-test.lisp / testkit-test.lisp / kg-test.lisp against their expected_*.txt files (plus lsp-test.py)
cargo run --release -- tests.lisp | diff - expected_tests.txt   # run a single golden file by hand

# Python bridge (optional `python` feature, enabled by default; needs maturin)
maturin develop            # install into active venv
python3 -c "import rusty; print(rusty.eval('(+ 1 2)'))"
```

**Versioning**: bump `version` in `Cargo.toml` as part of every commit that changes behavior — minor (`0.X.0`) for a feature/roadmap item, patch (`0.x.Y`) for fixes; docs-only commits don't bump. Rebuild after bumping so `Cargo.lock` stays in sync, and include both files in the same commit. Also update the `**Version:**` line at the top of README.md — it's the one spot that can't track `Cargo.toml` automatically (the REPL banner and `(help)` use `env!("CARGO_PKG_VERSION")`, so they follow for free).

There is no `cargo test` suite — correctness is checked by running a `.lisp` file and diffing stdout against a checked-in expected-output file. `benchmarks/agent_bench.lisp` is the Phase-3.3 deliverable benchmark (deterministic, no LLM) — timings, not golden output; don't add it to run_tests.sh. When adding new language behavior, extend `tests.lisp` (or `new-features.lisp`) and update the matching `expected_*.txt`, or add a new pair and a `run_test` line in `run_tests.sh`.

## Architecture

Three targets — `src/main.rs` (CLI/REPL), `src/lsp_main.rs` (`rusty-lsp`, a minimal stdio language server: paren/string diagnostics with positions, completion harvested from a real env, hover; tested by `lsp-test.py` in run_tests.sh), and `src/lib.rs` (PyO3 Python module) — all wrap the same core: `lexer.rs` → `parser.rs` → `eval.rs` + `interp.rs` → `env.rs`. Neither entry point should contain interpreter logic — new builtins/special forms go in `interp.rs`/`eval.rs` so both targets get them for free.

- **`src/lexer.rs` / `src/parser.rs`** — tokenizer and S-expression parser. `Parser::parse` is **lenient** (it closes an unclosed `(` at EOF and stops at a stray `)`) and stays that way because the REPL decides completeness with its own scanner (`InputStatus`, `main.rs`) before parsing, and the LSP reports its own positions. Every path that *runs* code goes through **`parse_checked`** instead (0.47.0 — `run_code`, the `load` special form, and the Python bridge's `check`): structural damage is an error there, because the lenient version made a truncated file (partial clone, interrupted write) **load clean with its tail silently swallowed into the last open form** — the failure mode this whole repo exists to refuse. Since parsing precedes evaluation, a refused load is all-or-nothing: even a complete definition earlier in a truncated file never takes effect. Backtick/comma/comma-at desugar at parse time into `(quasiquote ..)` / `(unquote ..)` / `(unquote-splicing ..)` list forms — there's no separate AST node for them. Scientific notation (`1e-20`, `2.5E+3`) lexes as a number since 0.22.0; an `e` not followed by `[+-]?digits` still starts a symbol. `Expr::List` is `Rc<Vec<Expr>>` (Phase 3.3 — cloning an Expr used to deep-copy whole function bodies on every call, ~4× of interpreter time); construct list exprs via `parser::elist(vec)`, and note you can't move elements out of a matched `Expr::List` — iterate by reference and clone.
- **`src/eval.rs`** — the evaluator. `eval()` is a single trampoline `loop { match &cur { ... } }`: special forms and tail positions rebind `cur`/`env` and `continue` instead of recursing, which is what gives TCO to arbitrary depth. When adding a new special form, follow this pattern (rebind + `continue`) rather than calling `self.eval` recursively, or deep recursion won't be stack-safe.
- **`src/env.rs`** — `Env = Rc<RefCell<EnvFrame>>`, a parent-linked chain of `VarMap` frames (lexical scoping via closure-captured `Env`). `VarMap = FxHashMap<String, Value>` (`rustc-hash`, Phase 3.3 — SipHash is pointless for interpreter-internal names), and frame maps are pooled: `EnvFrame::new` takes a recycled map from `arena::take_map`, `Drop for EnvFrame` clears and returns it (`recycle_map`). If you add a frame-construction path, go through `EnvFrame::new` or the pool is bypassed. `Value::List` is `LSlice` (an `Rc<Vec<Value>>` buffer + start offset, `Deref`→`&[Value]`, since 0.32.0) — cloning a list AND `cdr` are O(1) refcount bumps (cdr = same buffer, offset+1; it used to copy the tail, making every recursive traversal O(n²) — 30k-element walk 6.4 s → 28 ms). Trade-off: a live tail pins its whole ancestor buffer. Construct via `env::list(vec)`.
- **`src/interp.rs`** — builtins (`b!`/`alias!` macros register into the global `Env`), the stdlib loader (`std.lisp`, embedded via `include_str!` and used as a fallback if the file isn't found on disk), and the persistent `remember`/`recall`/`forget` Lisp-level memory system backed by `~/.rusty/memory.lisp` (auto-loaded by `make_env()` on every fresh environment — unrelated to Claude Code's own memory).
- **Command registry & coverage ratchet** (command-registry plan): `(command-registry)` is a special form (`src/eval.rs`) that walks the env chain to the root and returns every bound name with its kind; std.lisp's `help`/`apropos`/`describe` are driven from it (O(n log n) discovery), and the REPL's `/foo` sugar (`src/main.rs`) rewrites the input line to `(apropos "foo")` before it hits the normal eval path. Off-by-default coverage recording at the eval call site tracks which registered commands run under the golden suite; `run_tests.sh`'s coverage pass (`coverage-check.lisp`) is a hard ratchet — an untested command name fails the suite unless justified in `coverage-allowlist.lisp` (don't pad it to make the suite pass; add a real test).
- **`src/arena.rs`** — the live frame-map pool (Phase 3.3): `take_map`/`recycle_map`, thread-local, 1024-map cap. This *replaced* the old dormant mark/sweep arena sketch — that design couldn't work here (`Rc` values already reclaim at refcount zero, and its `mark()` had no value→slot mapping); see the module header and ROADMAP 3.3 for the reasoning. `recycle_map` requires an already-cleared map: clearing drops values, which can recursively drop other `EnvFrame`s that also borrow the pool — clear first, then hand over.
- **`src/llm.rs`** — **dead code**: not declared as a `mod` in either `main.rs` or `lib.rs`. The real LLM client (`call_llm`, used by the `llm` and `react-loop` special forms) lives inline in `eval.rs` and reads `RUSTY_MODEL` / `RUSTY_LLM_URL` / `RUSTY_SYSTEM` / `RUSTY_LLM_TIMEOUT_SECS` (default 120) env vars, defaulting to a local `llama-server`-compatible endpoint at `localhost:8080`. Calls share one lazily-initialized tokio runtime (`Evaluator::llm_runtime`) and carry a request timeout so a hung server can't freeze the interpreter.
- **Macros** (`defmacro`/`define-macro`, `src/eval.rs`) expand via ordinary evaluation of the macro body in an env extended with its (unevaluated) argument expressions. Hygiene is enforced at *definition* time: `hygienic_rename`/`hygienic_rename_top` rewrite identifiers a macro's own `quasiquote` template binds via `let`/`let*`/`letrec`/`lambda`/`do`/named-`let` into fresh gensyms, so the template's internal names can't capture, or be captured by, call-site code — but identifiers supplied through `,x`/`,@x` are left untouched (and free-identifier references inside a template, like a bare `table` symbol, are *not* rewritten to resolve in the macro's closure env — only unquoted references are). `gensym` (builtin) and this rename pass share one counter, `env::gensym_name`. A top-level `(eval-when (phase...) ...)` in a macro's body runs once at definition time (not once per expansion) in the env that becomes the macro's closure, letting a macro precompute something (e.g. one shared `gensym`'d name) instead of redoing it on every call; outside `defmacro`, `eval-when` just runs its body immediately, like `begin`. Expansion can be profiled: `eval::macro_profile` is a thread-local, off-by-default counter/timer wrapped around every macro expansion; `(macro-profile-on)` / `(macro-profile-report)` / `(show-macro-profile)` (the last in `std.lisp`) expose it. It attributes each expansion separately even when a macro expands into another macro (e.g. `repeat` expanding into `dotimes` counts one hit each).
- **`swarm.lisp`** (repo root, Phase 3.2 deliverable, also a golden test): proposer/verifier/certifier agents synthesizing verified functions via messages only — the verifier reuses `verify-candidate` (static gates first), rejections loop back as feedback messages. Deterministic by design; don't add nondeterministic output (timings, randomness) to it or `expected_swarm.txt` breaks.
- **`symreg.lisp`** (repo root, Phase 4.1 — pure Lisp library): symbolic regression by genetic programming. Candidates are Lisp expressions; fitness compiles each via `(eval (list 'lambda vars expr))` — the `eval` special form exists for this. Ops table `*sr-ops*` is `(name arity)` rows (`symreg-ops!` to extend — macro building blocks are legal vocabulary since `eval` expands them; measured 13→6 generations on Koza-1). Division inside candidates must be `sr-pdiv` (protected — the `/` builtin raises on zero and random candidates *will* divide by zero); the finalizer restores `/` in output only when the training data proves it safe. Deterministic via seeded LCG (`symreg-seed!`) — `symreg-test.lisp` is the 5th golden test, so don't introduce nondeterminism (or reorder PRNG draws: any change to draw *order* changes every discovered equation and breaks `expected_symreg.txt`).
- **`synth.lisp`** (repo root, Phase 4.2 — pure Lisp library): sketch-based synthesis. Sketches are quoted programs with `(?? id)` holes; `synth-fill` is a CEGIS loop over finite hole domains reusing 2.1's `verify-candidate` as the oracle (static gates still run first — don't bypass them), with oracle counterexamples feeding a cheap pre-filter. `synth-with-proposer` is the LLM seat (proposer → bindings, rejection+counterexample → feedback); `synth-extract-bindings` parses prose replies for the last valid bindings alist and treats them as data, never code. `synth-test.lisp` (6th golden test) synthesizes insertion sort and quicksort from one spec — deterministic, keep it that way.
- **`prover.lisp`** (repo root, Phase 4.3 — pure Lisp library): bounded proof assistant. Propositions are data; tactics are LCF-style goal transformers; the ONLY discharge path is `exhaust` → `check-exhaustive`, so "proved" = checked on every domain point, never an unbounded claim — don't add a tactic that discharges without evaluation. Strategy combinators (`tactic-seq`/`tactic-or`/`tactic-repeat`/`auto`) and `defproof` are macros; `defproof` registers into `*theorems*` only when no goals remain. `=` is numeric — boolean props need `equal?`. `prover-test.lisp` is the 7th golden test (it also re-synthesizes insertion sort via synth.lisp and proves it).
- **`robot.lisp`** (repo root, Phase 4.4 — pure Lisp library): deterministic control loops (`control-loop`/`control-until` — pure world-step + pure controller = reproducible trajectories; per-tick deadline misses counted and returned as data) and safety verification (`verify-controller` = the inductive safety step over finite state domains, `verify-actuation` = actuator bounds from any state; both via `check-exhaustive`). `robot-test.lisp` (8th golden test) proves a corridor robot's safety inductively and shows a reckless controller rejected — keep the world integer-valued (exact arithmetic is what makes exhaustive state coverage meaningful).
- **`pkg.lisp`** (repo root, Phase 5.2 — pure Lisp library): registry-less package manager. A package = a git repo with a `package.lisp` manifest; installs into `~/.rusty/packages/` from any git URL, transitive deps, no central registry (hosting one is an owner decision). `pkg-test.lisp` (9th golden test) uses local `file://` fixtures — keep it network-free (it installs into the REAL `~/.rusty/packages/` + `~/.rusty/pkg-locks/` and cleans up after itself; anything you add there must too). Integrity (0.46.0, on `file-hash`): `pkg-fingerprint` = every file under a package + SHA-256, sorted, **`.git` skipped** (two clones of one commit aren't byte-identical there — skipping it is what makes fingerprints comparable across machines); `pkg-verify name expected` takes an **out-of-band** fingerprint; `pkg-lock!`/`pkg-drift` catch post-install drift (auto-locked by `pkg-install`; the lock lives *outside* the package tree so a `git pull` can't rewrite its own alibi). There is deliberately **no `(files ...)` hash key in the manifest** — a hash the package ships in its own repo proves nothing and would look like a guarantee. `pkg-dir?` detects directories by catching `dir-list`'s raise (there's no is-directory? builtin). Note two language-level facts it depends on: `load` evaluates at **top level** (global env) since 0.26.0, and the filesystem builtins (`file-read`/`file-write`/`file-append`/`file-delete`/`file-exists?`/`dir-create`/`dir-list`, `string-split`) only exist since 0.26.0 — before that agent-tools.lisp's tool bodies referenced builtins that didn't exist (unnoticed because tool bodies don't run at registration). `dir-list` output is sorted for golden-test determinism. **All fs builtins FOLLOW symlinks** — so a path-string-prefix "under the box?" guard is defeated by a symlink inside the box pointing out (read/write/append/dir-list/dir-create/file-exists? all escape; only `file-delete` is safe, unlink removes the link not the target). 0.42.0 adds two no-follow primitives for guards: `file-symlink?` (lstat, #t incl. dangling, #f on miss) and `file-realpath` (canonicalize; Nil on unresolvable). 0.45.0 adds `file-hash` (streamed SHA-256 via the `sha2` crate → lowercase hex; Nil on unreadable, since a vanished file is a *result* for an integrity check, not a crash; follows symlinks like every content-reading builtin). Its golden is a **known-answer test** against the published SHA-256 vectors for `"abc"` and empty input — that's what pins it to real SHA-256 rather than to whatever we compute today; keep it that way. wuwei's `safe-under?` (guards.lisp) is the reference guard built on them; residual leaf-level TOCTOU remains a kernel-sandbox concern (see wuwei USE_CASES).
- **`testkit.lisp`** (repo root, Phase 5.2 — pure Lisp library): `deftest`/`test-run` registry+runner (catches raises, per-test report, boolean result), raising assertions (`assert-eq`/`assert-close`/`assert-true`/`assert-false`/`assert-raises`), `bench-median`/`bench-report`. Never print benchmark timings in a golden file — assert on their sanity instead (see testkit-test.lisp).
- **Knowledge graph** (Phase 1.3, resolved 2026-07): `src/kg.rs` — thread-local, insertion-ordered, deduped triple store (`kg-add!`/`kg-clear!`/`kg-count`/`kg-triples` builtins in `interp.rs`); `kg-query` takes a list of `(s p o)` patterns where `?`-prefixed symbols are variables shared across patterns, solved conjunctively with per-pattern best-index selection (s-index if subject bound, else o-index, else p-index, else scan) — indexes are keyed by **display strings** (injective across stored types since strings print quoted). N-Triples interop (`kg-save-ntriples`/`kg-load-ntriples`): symbols ↔ `urn:rusty:` IRIs (symbols containing `:` pass through as raw IRIs), strings ↔ escaped literals, numbers ↔ `xsd:double` — a *format* bridge, not a database dependency; beats rdflib ~10–29× on identical 60k-triple files (~10.4× load / ~20.2× grandparent / ~28.3× type+age, ranges not points) (`benchmarks/kg_bench.lisp` + `kg_rdflib_bench.py`, not in run_tests.sh; `kg_sweep.sh` drives them across scales — re-measured + swept 2026-07-15: the lead holds from 600 to 900k triples and never inverts, but the grandparent-join multiple *shrinks* with scale, 294× at 599 triples → ~17× asymptote, because rdflib's fixed SPARQL setup cost dominates tiny graphs — quote the asymptote, not the small end). Forward-chaining rules are pure Lisp on top (`kg.lisp`: `kg-rule!` body+head patterns, `kg-infer!` to fixpoint — counts only *new* triples, so dedupe in `kg-add!` is what makes the fixpoint terminate). All kg ops classified effectful in `effect_check.rs`. `kg-test.lisp` is the 12th golden test.
- **Actor message passing** (Phase 3.2, `std.lisp` — pure Lisp, no evaluator changes, same library-phase pattern as 1.3): `agent-spawn`/`send!`/`run-agents` + introspection (`agent-names`, `mailbox-count`, `agents-idle?`, `agent-reset!`). Deterministic cooperative scheduler: agents visited in spawn order, one FIFO message popped per step (dequeued *before* the handler runs, so self-`send!` works), handler runs to completion; `(quiescent n)` on empty mailboxes or `(hit-max-steps n)` at the cap (default 10000). Errors return as data (`(error no-such-agent ...)`), not raises. Deliberately single-threaded — `Rc`-based runtime, no threads; handlers hold state via `set!` on enclosing bindings.
- **Execution tracing** (Phase 3.2, `src/trace.rs`): thread-local, off-by-default event log — `trace-on/off/clear/report/dropped` builtins + `trace-event` for Lisp-side events (no-op when off; std.lisp's `send!`/`agents-step` call it unconditionally). Report rows `(seq t-micros kind name dur data)` are pure data (round-trips through `save-model`). Note the asymmetry: `tool-call`/`apply` paths record durations, but the first-class tool call path emits entry-only `tool-enter` — it's a TCO `continue`, so don't try to add an end-time there without breaking tail calls. 100k cap + dropped counter.
- **Checkpoint/restore** (Phase 3.2, `src/checkpoint.rs` + the `checkpoint` special form in `eval.rs`): `(checkpoint "f.lisp")` writes the global env as plain Lisp source (restore = `(load "f.lisp")`). Baseline filtering: a pristine env (builtins + std.lisp + memory, cached per thread) is skipped by *name* for code values but by *value* for pure data — that's what lets modified stdlib data (`*agents*`, `*mailboxes*`) checkpoint while stdlib functions don't. Lambdas serialize as source and re-close over the restored global env (let-bound captures are lost — durable actor state belongs in globals); `Value::Native`/`Value::NativeGrad` are unserializable by design and are listed in the file's header comment. If you add a `Value` variant, extend `value_to_expr`/`is_pure_data` here or new values will silently land in the "not serialized" list.
- **Tools/agents** (`deftool`, `tool-call`, `react-loop`, `src/eval.rs`) are a separate `Value::Tool` variant from `Lambda`; `agent-tools.lisp` (auto-loaded by std.lisp) registers filesystem/shell/LLM tools; `(agent goal)` drives a ReAct loop (ACTION/INPUT/OBSERVATION/FINAL) against the LLM client above. Tools are also **first-class callables** (Phase 2.3): the eval call dispatch and `apply_value` both handle `Value::Tool` like a fixed-arity `Lambda`, so `(my-tool arg)` and `(apply my-tool args)` work without `tool-call` (since 0.20.0 `apply_value` also handles `Native`/`NativeGrad`, so `apply`/`map` work on compiled functions too). The contract layer on top lives in std.lisp: `deftool-spec` (param types, allowed effect ops, precondition, deps → `*tool-specs*`), `safe-call` (checks contracts *before* the body runs), and `certify-tool-chain` (spec presence + effect honesty via `check-effects` on the tool body + dependency order). **`*tool-specs*` is global and keyed by tool NAME, and `deftool-spec` REPLACES that name's entry** — so a caller that certified a tool at boot cannot assume `safe-call` will later look up the spec it certified, and *cannot check*, since a precondition is a code value and code values are never `equal?` to anything (SPEC §equality). `safe-call-with-spec` (0.48.0) takes the spec explicitly so a caller can enforce the one it pinned; `safe-call` is that function with the lookup in front, sharing one implementation so the checks can't drift. wuwei's certificate dispatch is the consumer.
- **`src/rust_jit.rs`** — `defrust` compiles a *restricted* numeric subset (numbers, params, `let`/`let*` locals, `+ - * /`, the numeric builtins `sqrt expt abs mod floor ceiling round min max sin cos tan atan atan2 exp log`, `if`/`cond` with comparison/`and`/`or`/`not` conditions, self-recursive calls — everything is `f64`; no lists/strings/closures/global capture) to real Rust. `defrust*` (Phase 3.3) compiles a *group* of functions into **one** `.so`, so calls between group members are plain Rust calls — mutual recursion works; that's the only way compiled functions call each other (functions from *separate* `defrust` invocations still can't — that's cross-`.so` linking, still cut). Semantics notes: `let` binds via Rust tuple destructuring to preserve parallel semantics (inits can't see each other's bindings; `let*` is sequential) — don't "simplify" it to sequential `let`s; `cond` requires a final `else` (every path must produce an f64); one documented divergence from the interpreter: `(mod x 0)` is NaN compiled vs an error interpreted (the ABI has no error channel). Codegen generates source with a fixed `extern "C" fn(*const f64, usize) -> f64` ABI (uniform regardless of arity), shells out to `rustc --crate-type cdylib -O` (cached by a hash of the generated source, under `~/.rusty/jit-cache/`), and loads the result with `libloading`. Lisp names get sanitized to valid Rust identifiers (`fib-native` → `rusty_fib_native`) — don't assume the Rust symbol matches the Lisp name literally. Backing storage is `Value::Native { lib: Rc<Library>, fn_ptr: *const () }`: `fn_ptr` is a function pointer detached from `libloading::Symbol`'s lifetime via a raw-pointer transmute (see `rust_jit::call`), kept valid only because the `Rc<Library>` clone inside the same `Value` is never dropped while it's in use. Measured real speedup on tree-walked vs. compiled `fib(30)`: ~8.2s vs. ~0.007s (cached) — see `docs/ROADMAP.md` 1.2.
- **Symbolic differentiation** (`grad` builtin, `interp.rs` → `eval::symbolic_derivative`) is AST rewriting via calculus rules (`+ - * / expt sqrt sin cos tan atan exp log`, plus `if`), not numeric/tracing autodiff — `(grad (lambda (x) expr))` returns a new callable `Lambda` whose body is the derivative expression, differentiated with respect to the lambda's *first* parameter (other free variables are treated as constants).
- **`src/graph_ir.rs`** — a computation DAG (`Graph`/`Node`/`Op`) over the restricted numeric subset of `defrust` *plus* the tensor ops (`TAdd/TSub/TMul/TDiv/MatMul/Transpose/TSum` — recognized as `tensor-add` etc. in lambda bodies), built via hash-consing (an `Interner` that dedups `(Op, args)` during construction — this *is* the CSE, not a post-hoc pass). `optimize()` then runs constant folding (`fold`, including pruning an `if` branch when its condition is constant — the untaken branch just becomes unreachable) and dead-code elimination (`dce`, mark-and-sweep from `Graph::output`, which is what actually removes what folding orphaned); all of it shape-agnostic, so tensor expressions get CSE/pruning/DCE for free. Folding stays scalar-only by construction: tensors have no literal form in the Expr subset — they enter a graph only through `Param`s (`graph-eval` accepts `Value::Tensor` arguments, marshalled to `graph_ir::GVal`, the IR's number-or-tensor runtime value). Scalar `+ - * /` stay scalar in the IR too — a tensor hitting them is a clean eval-time error, mirroring the language level where `tensor-add` (not `+`) is the tensor op. **Reverse-mode autodiff** (Phase 3.1 deliverable) lives here too: `backward()` sweeps the (already-optimized) graph in reverse, emitting gradient rules as more nodes into the same interner — forward/backward CSE against each other — and the `graph-grad` builtin returns `(loss grad-per-param...)` from one `eval_graph_outputs` pass over the multi-output-optimized graph (`optimize_outputs`; plain `optimize` is the single-output wrapper). Three ops exist only in generated gradient graphs, with no surface syntax: `Step` (relu's derivative), `SumTo` (undoes scalar broadcast during accumulation), `Expand` (`tensor-sum`'s gradient). `Relu` has surface syntax and a matching `relu` builtin. Data-dependent `if`/comparisons refuse differentiation (constant-condition `if` is pruned *before* `backward`, so it's fine); the scalar-loss check happens at eval time since shapes aren't static. Gradients verified bit-for-bit against PyTorch float64 autograd, and the trained-layer benchmark beat 1-thread PyTorch at small sizes (see ROADMAP 3.1) — but note `graph-grad` rebuilds+optimizes the graph on every call and matmul is naive O(n³); caching/fusion is 3.3's territory. This is deliberately separate from the symbolic `grad` builtin (scalar-only, one derivative expression per parameter). Codegen backend (Phase 3.3 kernel fusion): `graph-compile` (builtin, `interp.rs`) → `rust_jit::compile_graph` emits the optimized DAG as one straight-line Rust function (every node a `let`, in the nodes' existing topological order; `If` compiles to the same *eager* select `eval_graph` uses — both branches computed, then chosen — don't "fix" that to a lazy branch, it would diverge from interpreter semantics) and returns a callable `Value::Native`; ~29× over tree-walk on a 282-node kernel. Scalar-only: tensor ops are rejected at compile time. The tensor half is `graph-compile-grad` (example-args give the shapes) → `rust_jit::compile_graph_grad`: static shape inference (`graph_ir::infer_shapes` — mirrors `eval_nodes`' rules exactly, incl. scalar broadcast and the loss-must-be-scalar diagnosis; the builtin pre-checks the *forward* graph's output shape before `backward()` so a tensor loss gets the clear error, not a confusing internal one) makes every buffer size/loop bound/matmul dim a compile-time constant; returns `Value::NativeGrad` (own ABI `fn(*const f64, *mut f64)`, flat in/out at static offsets; single-shape — recompile for new shapes). Fused matmul and the interpreter's two matmuls (`graph_ir::t_matmul`, `matmul` builtin) all use slice-based ikj with the **same per-element summation order** — results are bit-identical across `graph-grad`/`graph-compile-grad` and the earlier PyTorch bit-for-bit claim survives; don't change one loop order without the others. JIT `rustc` uses `-C opt-level=3` and `RUSTC_FLAGS` is folded into the cache hash (flag changes invalidate cached `.so`s). `graph-eval` still interprets via `eval_graph` (and rebuilds the graph each call — that's the overhead compiling removes: ~6× on small training loops, but only ~1.14× at 64×256→64, where naive-O(n³) matmul flops dominate both paths and PyTorch/BLAS still wins that shape ~2.5×). **The win from fusing shrinks as shapes grow.** Re-recorded + fixed 2026-07-15 (`benchmarks/tensor_bench.lisp` + `tensor_torch_bench.py`, one machine state per A/B). The medium shape was *slower* compiled than interpreted from the feature's release until v0.44.0, hidden behind a recorded "parity" claim nobody rechecked. Two passes fixed it, and the first was half wrong — **the profile REFUTED the pre-registered guess** that Rust-side ABI marshalling dominated (75% of the workload was inside `call_native_grad`, but ~all of it had the kernel on the stack): **v0.43.0** the *generated kernel* was `.to_vec()`-ing every input tensor (~295 KB/call) and cloning on `SumTo` same-shape identity (~164 KB/call) — both now borrow (−8.9% medium, −6.5% small); **v0.44.0** the caller's flat-buffer copies (~885 KB/call) were the structural half that WAS real — `NativeGrad`'s ABI is now `fn(*const *const f64, *const *mut f64)`, one pointer per argument and per output, so tensors are read where they lie (`Rc<Vec<f64>>` is already contiguous) and each result is written straight into the buffer that becomes it (−10.1% medium, flipping the JIT ahead of the interpreter at last). Cumulative 143.3→114.6 ms. If you touch this codegen: `Op::If` tensor arms must use `.to_vec()` (not `.clone()`) so a borrowed-param arm and an owned-Vec arm share one type — that is what makes the borrowing safe. `graph-compile-grad` is in `coverage-allowlist.lisp` (goldens avoid rustc), so **the suites passing is NOT evidence for grad-codegen changes** — use an interp-vs-JIT equivalence check (exact equality, incl. a relu-boundary shape). Don't quote wall-clock absolutes from these docs — they're machine-dependent and the old ones had drifted enough to invert the medium-shape verdict; re-run the benchmarks.
- **Native tensors** (Phase 3.1): `Value::Tensor { data: Rc<Vec<f64>>, shape: Vec<usize> }` (`src/env.rs`), flat row-major, clone = refcount bump like `List`. Builtins + helpers (`nested_to_tensor`/`tensor_to_nested`/`tensor_binop2`) live in `src/interp.rs`. Deliberately no external ML crate (candle/burn count as external too — see the roadmap design constraint). `value_equal` compares shape+data; `type-of` → `tensor`; display shows values only for ≤8 elements. Graph IR accepts tensor expressions and tensor arguments too — see the `graph_ir.rs` bullet above for how. `save-model`/`load-model` (`interp.rs`, Phase 3.1) persist *data* values (incl. tensors, and Graph IR output, which is plain list data) as a versioned JSON envelope via `serde_json`, with symbols/tensors as tagged objects so they round-trip losslessly — deliberately unlike the lossy `json-encode`; code values (lambda/tool/macro) and NaN/Inf are rejected by design (live-environment serialization is 3.2's checkpoint/restore).
- **Python bridge** (`src/lib.rs`): `RustyInterp` is stateless (fresh `Env` per call). `RustySession` fakes statefulness by **replaying its entire eval history into a fresh `Env` on every call** rather than holding one persistent `Env` — a deliberate choice to avoid `Rc` across the PyO3 boundary, but it means side effects (e.g. `shell`, file I/O) replay too.

Development follows the phased checklist in `docs/ROADMAP.md` (see also `docs/ARCHITECTURE.md`, `docs/AI_AGENTS.md`); check it for what's next before assuming a feature is unplanned. **Design constraint that applies to all of it**: Rusty has zero external runtime dependencies — no Lean 4, no TLA+, no PyTorch/JAX/candle/burn, nothing that isn't either the Rust standard library, a Cargo crate, or `rustc` itself (already required to build Rusty, which is why `defrust` can shell out to it without it counting as a new dependency). Where the roadmap talks about "verification" or "ML integration," it means a self-built equivalent, benchmarked against external systems, never depending on them — see `docs/ROADMAP.md`'s "Design Constraint" section for the full reasoning (this is *why* Phase 2.1 no longer says Lean 4/TLA+, and Phase 3 no longer says PyTorch/JAX interop). Phase 1.3 ("Neuro-Symbolic Bridge Layer") is explicitly a *library* phase — `defun-constrained`/`logic-loss`/`implies` live in `std.lisp` as plain macros, not new Rust special forms; there was no need to touch the evaluator for them. Note `assert` is a macro there (not a function, as it might look at a glance) — it needs the literal unevaluated condition to build a useful default error message.

`define-typed` (std.lisp, Phase 2.2) is **runtime-checked gradual typing** — a call-time contract check via the same `<type>?` predicates already in the language, not static analysis. If you touch it: its own `let`-bound temp is generated with `(gensym "result")` and spliced everywhere via unquote rather than written as a literal template binding — a literal binding there would get renamed by the Phase-1.1 hygiene pass (since it's inside a `quasiquote`) but a helper function's own separately-evaluated quasiquote generating a *reference* to that same name wouldn't see the rename, producing an `Undefined` error. This bit us once already; see the `define-typed` macro for the fix and `git log` (`docs/ROADMAP.md` 2.2 note) for the full story. **`src/type_check.rs`** (Phase 2.2) is the actual static half: `check-types` walks a lambda's body *without executing it*, tracking a `TyEnv` (variable name → statically-known `Ty`) through `if`/`let`/`let*`, narrowing on a recognized `<type>?` predicate test in an `if` condition and propagating through `let` init expressions. Conservative by construction — `Ty::Unknown` is never flagged, so it only reports what it can prove. It consults a thread-local signature registry (`type_check::register_signature`, populated by `define-typed`'s expansion via the `register-signature` builtin) for calls it doesn't otherwise recognize, so `define-typed` functions check statically too — declared param types are enforced at call sites and the declared return type flows onward. Plain `define`d functions still infer as `Unknown`.

**Proof-by-checker loop** (std.lisp, Phase 2.1): `synthesize-verified`/`verify-candidate` gate proposer-suggested candidates through the 2.2 checkers. The load-bearing invariant is gate *ordering* — static gates (`check-effects`, `check-types`) run first and must reject without the candidate ever executing; only then does `check-exhaustive` (which runs the candidate) fire. Don't reorder them. `eval-string` (builtin) evaluates text in a *fresh* env — that's a scoping choice for LLM-proposed code, not a sandbox; the static-first gate ordering is the actual guard. Contrast the `eval` special form (Phase 4.1, `eval.rs`): `(eval datum)` runs a data value as code in the *current* env, TCO'd (it rebinds `cur` and continues) — pure data only, code values inside the datum become Nil. Pick per use: fresh-env isolation → `eval-string`; building code as data at runtime (GP, macros-by-hand) → `eval`. `llm-proposer` needs a live llama-server (scripted proposers otherwise); it has been live-verified end-to-end on the owner's local model.

**`check-exhaustive`** (builtin, Phase 2.1) exhaustively runs a property over the cartesian product of finite domains — `'verified` or `((args...) reason)` counterexamples, 1M-combination cap. It's the self-contained "model checking" replacement; verification here means *ran everywhere*, not sampled. Note std.lisp's `range` is accumulator-based specifically because the naive cons-position recursion overflowed the Rust stack (~200 elements, debug build) — don't "simplify" it back; and remember `cons` is still O(n) per call (copies into a fresh buffer — prepending can't share a buffer that grows left), so cons-building is O(n²); `cdr`-traversal is linear since 0.32.0 (see the env.rs bullet), so accumulate+`reverse` is the linear build idiom. `benchmarks/list_bench.lisp` records the numbers (timings — not in run_tests.sh).

**`src/effect_check.rs`** (Phase 2.2, the last item) — `check-effects` walks every statement in a lambda's body (not just the last/return one, unlike `check-types`/`grad` — side effects in earlier statements matter here) and reports operations from a fixed effectful classification (`effect_reason`), same conservative philosophy: unrecognized/user-defined calls are never flagged. It specifically distinguishes `quote` (skipped — inert data) from `quasiquote` (literal template parts skipped, but `unquote`/`unquote-splicing` contents *are* checked, since those actually run) — a real, tested distinction, not an incidental one.
